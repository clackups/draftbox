Draftbox
========

This project implements a Git hosting service for non-technical
users. The primary interface is HTTP, using standard Git HTTP
intarface with granular access tokens and the web interface for user
interaction.

The backend uses its own local Git repository as a database engine:
all user accounts, their preferences, security settings, access
tokens, etc, all are saved as Git data. The backend interacts directly
with the repository using libgit2, without the need for a checked-out
working directory.

The programming language is Typescript. The running environment is
Nodejs, but Bun or Deno should also be possible.

Users register with their email addresses, exclusively via oAuth
providers, such as Goole or Github. The backend confuguration should
allow the following options for user registration:

* anyone can register: the user account is created as soon as they authenticate themselves in oAuth;

* registration by invitiation links: the user is communicated an invitation link which allows them regiister a new account;

* pre-registrarion via administrative API: the backend process, such as payment processor, instructs Draftbox that a user with given email address is allowed to register.

In the web UI, the user can create new repositories, edit Markdown and
text files in the browser, add tags. If the user activates advanced
mode, the GUI allows creating and browsing branches. In simple mode,
only the "main" branch is available in each repository.

The access token GUI allows the user create new tokens for global
access or repository-only access. By default, read-write access is
asigned, but the user may set a read-only token too. Tokens are
permanent by default, but the user can also set a limited validity
time (1, 3, 6, 12 months).

The user can assign a one-time 8-digit password to a token. The
password is randomly generated by Draftbox. Draftbox provides an API
that returns the token in exchange to this 8-digit password. The
password can only be used once.

Each repository can be set to public or private. Public repositories
are available for browsing to unauthenticated or authenticated users
and are available for unauthenticated Git HTTP access. When the user
creates a repository, private is the default option, and the interface
should explicitly explain the user what a public repository means.

The backend configuration defines one or several administrator
accounts: they are email addresses which are authenticated by one of
trusted oAuth providers.

The administrator, in addition to standard user functions, is able to
manage the service:

* Block or unblock the users. A blocked user cannot access the service and their publlic repositories are hidden.

* Delete users.

* Customise the web interface brandiing and theme.

The web UI should support multiple languages. The language that is
selected by the user is stored in their preferences. English is
default. For now, add Ukrainian and German.

Git SSH access is not foreseen at the moment, but the data schema
should be flexible enough to add SSH keys in the future.
